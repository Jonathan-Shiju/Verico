# What anti-money laundering is

AML is collections of techniques to disguise illegal-funds amongst millions of legitimate-transactions.

It's an ever-evolving type of fraud which requires analysis of money trails across multiple isolated transaction groups.

These groups are usually spread across multiple days or even weeks which means gathering related information is crucial.

# What Verico does

- Verico processes millions of transactions into Graphs, which are processed to be enriched by static user-profile information
- Verico allows investigating leads and cases which are generated during ingestion of transactions and transactions which are picked up by investigators
- Verico functions as a single source of information storing flagged suspicious accounts and corresponding payments
- Verico also automates the process of generating documentation throughout the case filing process
- Verico also helps in documenting the reasoning for the decision to keep or dismiss leads

# How we simulate the environment

We use IBM Transactions for Anti Money Laundering Dataset with High Percentage of Laundering transactions to simulate the process of investigation.

Transactions are largely streamed in the real world hence, we process the transactions and replay them in a stream.

Since the transactions are spread across 10 days, for simulation purposes we replay them over a fixed duration (10 minutes) by scaling the difference in timestamps of two consecutive transactions.

# How graphs help

Analysing payment trails are complicated if stored in the traditional sense. As such transactions are streamed at high rates and hence, transforming data on fly may add more latency.

Graphs are naturally the best & ideal format to store incoming transactions, wherein accounts are linked via transactions and user-profile information from KYC enrich the graphs.

Transformation after ingestion of data through graph-based algorithms are highly-efficient to validate transactions and to generate leads.

Reasoning becomes easier even through multiple hops.

Thus, FalkorDB is used to follow money trails.

# Features in Verico

## Lead generation

There are various forms of leads generated by Verico some of which are loops - money end up in senders accounts across multiple hops, residues - pooled residues wherein small payments are gathered and further sent out, split residue where one huge payments are sent in multiple small payments.

The remaining are counted as open chains.

## Risk analysis

Accounts can be flagged based on suspected fraud transactions including counterparty flagging, this essentially helps in case building and scoring risks of transactions.

## Documentation

Decisions on leads are made by investigators and if kept, Verico generate case files which document the conversation leading up to the moment. Includes, narrative (conversation log), payments, parties involved, tool calls (explanability).

## Payment walk

Current transactions are displayed as graph with all information and metadata, highlighting flagged accounts and accounts part of leads.

## Persistent session memory

Yet to be implemented. Tool calls, account and payment citations, and the multi-turn conversation text are stored as pointers in the graph. The pointers point to the data in Redis.

# Tech stack

- Redis stores static files and data
- Kafka streams the transactions
- FalkorDB stores the transactions and entity links, and the session pointers
- Langchain runs the operator conversation
- FastMCP exposes the graph reads as tools
- FastAPI serves the workspace API
- Next.js is the site

# Implementation

A payment file whose name ends in `_Trans` is loaded into Redis in hourly buckets. Replay publishes that file onto a Kafka topic and compresses the original time span into a shorter wall-clock duration. For this dataset that duration is 10 minutes.

Ingest reads the topic from the start and writes FalkorDB. Each window covers 8 days, and a new window starts every 4 days, so a payment near a boundary is stored in two graphs. The account id, the bank number with leading zeros removed and then the account number, is what joins those graphs. There is no edge from one window into the next.

The loop detector reads the same stream in time order. A later outgoing payment continues a branch when its amount stays near the amount already followed. A payment back to an account already on that branch is a closed loop. Two or more hops that never return are an open chain. Both are written to `aml:loops`.

After the windows are stored, one pass writes marks to `aml:flags` and another writes pooled and split cases to `aml:cases`. The graph server exposes those reads as tools. The operator session calls the tools and returns one JSON object: the markdown reply, and three commands the officer would type next. The API streams that reply to the workspace.

# Issues faced

## Ingestion at scale

FalkorDB's `MERGE` of accounts created in the same query slows once a query passes about 1000 new nodes, so ingest writes accounts and payments in chunks of 1000. A payment is merged on its id, so a row that arrives twice does not become a second edge. Indexes sit on the account id, the entity id, the payment id, and the payment time.

A `WHERE id IN` filter is dropped when the next clause expands a relationship from that account, so the fan-in, fan-out, and residue queries carry the account forward with `WITH` before they count edges. A lookup of one payment by id leaves both ends of the edge unlabeled. Labeling them makes Falkor scan every account before it uses the payment-id index.

## Persistent memory across sessions

A table row for every turn would copy the lead, the accounts, and the payments onto each line. Finding every conversation that touched one loop would scan those rows. The words of a turn stay in a Redis stream, one stream per session. FalkorDB keeps a session node and an edge to each subject that conversation named: a loop, an account, or a payment. The edge is the pointer. The text stays in Redis.

The running conversation still holds its own copy in memory. A new session does not load the stream back into the model yet.

## Prompt suggestions

A second model call, made only to invent the next prompts, came back as questions to the officer and waited on another round trip. The reply is now one JSON object. The `reply` field is the markdown. The `prompts` field is three commands the officer would type, separated by a comma and a space. The workspace renders the markdown and puts those commands under the composer.

## Transaction comprehension

A paragraph that names several accounts and payments is hard to follow once the trail is more than one hop. The workspace draws the payments as a graph, with the time, the amount, and the method on each edge. An account with a mark is drawn in red. An account that is on a lead, and has no mark, is drawn in brown. The selected payment keeps a red outline.
